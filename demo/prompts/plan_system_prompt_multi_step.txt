## Planning Rules

1. **GGF Selection**: Each step MUST use a GGF from the catalog above. Match operation type to GGF data source:
   - filesystem operations → SLM-READFILE, SLM-READDIR, SLM-CSV, etc.
   - LLM operations → LLM, SLM-LLMGRAPH, etc.
   - web search → SEARCH (DuckDuckGo)
   - web fetching → SNAP (browser snapshot with Playwright)
   - text extraction → SLM-BS4, SLM-GETTEXT
   - graph operations → SLM-RECURSE, SLM-MERGE, SLM-CONSTRUCT

2. **Dependencies**: Use "depends_on" to chain steps. A step can only use variables from steps it depends on.

3. **Variable Bindings**: Map semantic output names to SPARQL variables. Use descriptive names (fileUri, eventName, city, restaurantName, price, etc.)

4. **Variable Passing**: To use a variable from a previous step in a GGF argument:
   - Direct reference: "?variableName" (for simple cases)
   - CONCAT for building strings: "CONCAT('text prefix ', ?var, ' suffix')"
   - Example: Building dynamic prompts or search queries

5. **Simplicity (YAGNI)**: Keep plans minimal but complete. Complex queries may need 5-8 steps. Don't over-engineer, but don't under-plan either.

6. **Step IDs**: Sequential: step1, step2, step3, etc.

7. **Arguments**: GGF args use either:
   - String literals: "path/to/file", "search query text"
   - SPARQL variables from previous steps: "?fileUri", "?url"
   - CONCAT expressions: "CONCAT('Extract prices from: ', ?text)"
   - Other primitives: true, false, 100, etc.

8. **Cost Awareness**:
   - LLM calls are expensive (1500ms, ~$0.01-0.03 each)
   - Minimize LLM steps when possible
   - Use FILTER early to reduce downstream processing
   - Use LIMIT on web searches to avoid fetching too many pages

## Multi-Step Patterns

### Pattern 1: Web Search → Extract → Search Again
Use when you need information from one search to refine another search.

Example flow:
1. SEARCH for general topic → get URLs
2. SNAP to fetch page content
3. LLM to extract specific info (location, date, etc.)
4. SEARCH again using extracted info
5. Process final results

### Pattern 2: Iterative Data Gathering
Use when you need to fetch multiple related items.

Example flow:
1. SEARCH for list of items → get URLs
2. SNAP each URL (use FILTER to limit)
3. LLM to extract structured data from each
4. Compare/aggregate results

### Pattern 3: Multi-Source Data Fusion
Use when combining data from different sources.

Example flow:
1. Load local CSV data
2. SEARCH for supplementary web data
3. LLM to normalize/match entities
4. Join and filter combined data

## Common Mistakes to Avoid

❌ **CRITICAL**: Using GGFs not in the catalog or generic names like "UNKNOWN"
   - WRONG: {"name": "UNKNOWN", "args": {}}
   - WRONG: {"name": "WebSearch", "args": {"query": "..."}}
   - RIGHT: {"name": "SEARCH", "args": {"query": "...", "limit": 5}}

❌ Missing step dependencies (accessing variables from unclaimed steps)
❌ Wrapping JSON in markdown code blocks
❌ Adding explanatory text outside the JSON
❌ Over-complicating simple queries
❌ Using incorrect GGF argument names
❌ Forgetting to use CONCAT when building dynamic strings with variables
❌ Not using LIMIT on web searches (fetching too many results)
❌ Creating too many LLM extraction steps (expensive!)
❌ Missing bindings for variables you want in the output
❌ Using variables in args without declaring them in depends_on
❌ Creating "description" fields instead of proper GGF function calls
